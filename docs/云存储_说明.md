# 云存储（云存）说明 — 录像 SDK 是否支持？

## 结论

**录像 SDK（recorder_sdk / RSDK）本身不含云存储**——它是**本地裸盘直写**的存储引擎（no-FS + 定长块 + 索引 + 加密 + 多盘均衡）。
全量 grep `cloud/云存/upload/oss/s3/ftp/webdav/remote backup` 在 src/include/设计文档中**零命中**。
云存是**独立关注点**（上传/同步），不该塞进 RSDK；应在其**之上**加一层。

## RSDK 已提供的、可供云存层复用的"钩子"

云存不用从零做，RSDK 现成的东西正好是云存的输入：

| RSDK 能力 | 云存怎么用 |
|-----------|-----------|
| `rsdk_backup_export` / `_seg` → MP4/fMP4 片段到本地 path | 云存"事件片段上传"直接消费导出的 clip |
| 事件系统：事件段打标 + `rsdk_pic` 抓拍 + `rsdk_meta` JSON | 事件触发 → 上传"事件 clip + 缩略图 + 元数据"（NVR 云存最常见形态） |
| `rsdk_index_query` 段索引（时间→段） | 精确定位要上传的时间范围/段，避免全量传 |
| **muxer 扩展** `rsdk_backup_register` | 加一个"上传 muxer"：把 fMP4 分片直接写到 HTTP/云而非文件，做**连续云备份** |
| 加密（AES-256-CTR）| 上传前即密文，云端零明文 |

## 两条落地路线

### 路线 1：TUTK VSaaS（推荐，路径最短）
TUTK SDK 自带 **VSaaS**（Video Surveillance as a Service，云录像服务）：
`third_party/tutk_sdk/Include/VSaaS.h`。本项目已集成 TUTK P2P（④），**复用同一套 UID/鉴权**即可开云存，
事件 clip / 连续录像推到 TUTK 云。工作量最小。

### 路线 2：通用云（S3 / 阿里云 OSS / 自建 HTTP）
新增 `components/cloud_storage`（与 `cloud_tutk` 并列，位于 recorder 之上）：
- **事件驱动**：事件触发 → `rsdk_backup_export` 出 clip + 取 `rsdk_pic` 缩略 → 上传 + 回传 URL；
- **连续备份**：注册"上传 muxer"，录像旁路把 fMP4 分片周期上传；
- 断点续传、配额、网络退避、加密密钥托管在本层。

## 架构位置

```
                 ┌───────────────────────────┐
                 │  app/event (事件联动)      │  事件触发
                 └───────────┬───────────────┘
                             ▼
   ┌──────────────┐   ┌───────────────────────┐
   │ recorder(⑤)  │──►│ cloud_storage(新, 待补)│──► TUTK VSaaS / S3 / OSS / HTTP
   │ 导出clip/抓拍 │   │  事件clip+缩略+元数据上传 │
   └──────────────┘   └───────────────────────┘
   本地裸盘(⑥ storage)          云端(异地容灾/远程回放)
```

## 现状小结

- ⑥ 本地存储：裸盘方案已实现（`components/storage`）。
- 云存：**未实现，但架构位置清晰、RSDK 钩子齐全**。要做建议先走 **TUTK VSaaS**（复用④），
  或新增 `components/cloud_storage` 走通用云。属于 recorder 之上的独立模块，**不改 RSDK**。
