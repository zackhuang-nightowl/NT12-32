# 拉流/预览/录像 — 参数集(SPS/PPS/VPS)兼容修复计划

> 状态:**已实现(2026-08-21)**,未提交、未上板编译验证(本机无交叉工具链)。
> 目标:修复个别相机导致的 VPU `scan first header error` / `264_dec trigger fail`,**不影响正常相机**。
>
> 已落地:fix1/1b/2(`stream_router.c`)+ fix3(facade `videoParameterSets` 取 SDP sprop → Annex-B,
> puller 连上 seed `par[]`)+ CMake 统一指向 `SDK/OnvifClientLibrary` + 删除冗余 `third_party/happytime_onvif_rtsp`
> (预编译 `libsrt.a`/`libsrtp2.a` 已随 OCL,link 不变)。数据源=相机 DESCRIBE 的 SDP,真实非猜测。

## 1. 现象

板级串口反复刷:

```
[H264Dec_OneFrameStart][642]ParserStart error! (-1)
[H264Dec_OneFrameStart] EN_VPU_EVENT_PIC_DONE  triggerHwRet = -1
[DE] {0,0,2} 264_dec trigger fail, ret -1
[DE] {0,0,2} scan first header error, ret -2, please refer to Novatek_HDAL_Playback_Issues_FAQ_en.doc
```

`scan first header error -2` = VPU 在码流开头扫不到有效序列头(SPS)。FAQ 名含 **Playback**,指向回放路径为主。

## 2. 根因

### 主因(回放):录像没有把参数集存进码流

- 录像入队 `stream_record_enqueue` 把 `is_param` 的参数集 NAL **直接丢弃**
  (`components/streaming/src/stream_router.c` 约 254 行 `... || nc->is_param) return 0;`)。
- 录像写的是**裸 `data`**(约 632 行连续录、646 行事件片段),**不是** Live 已拼好参数集的 `sbuf`。
- recorder 侧**没有**单独存 SPS/PPS 的地方(headers 内无 sps/pps/extradata 字段)。
- 结论:凡是**把 SPS/PPS 作为独立 NAL 发送**(不内嵌进 IDR AU)的相机,录下来的段首 IDR
  不含序列头 → 回放喂 VPU 即 `scan first header error -2`。

### 次因(预览 Live):参数集缓存为空时把 param-less IDR 喂了 VPU

- `have_params` 门控只护住 bootstrap 关键帧缓存(约 590 行),**没护住正常 live 起播**:
  `stream_live_drain` 在 WAIT_IDR 见到任意 `is_key` AU 就送解码(约 615 行 push 用 `nc.is_key`)。
- 当 `par_len==0`(刚连上 / 重连 / RESYNC 还没收到第一组 SPS,或参数集只在 SDP 的相机),
  送进去的是无序列头 IDR → `ParserStart error -1` / `trigger fail -1`,直到下一组 SPS+IDR 到才自愈。

## 3. 为什么是"个别设备"

H.264/H.265 相机发参数集有两种习惯:

- **内嵌型**(正常):SPS/PPS 内嵌进 IDR access unit(`has_param`)→ 参数集本就在帧里,录/放均正常。
- **分离型**(个别):SPS/PPS 作为独立 NAL 单独发 → 被录像丢弃,段首 IDR 无头 → 回放报错。

因此问题只出在分离型相机;修复对内嵌型相机**字节级不变**。

## 4. 计划改动(仅对"缺内嵌参数集"的相机生效)

| # | 位置 | 改法 | 正常设备为何不受影响 |
|---|------|------|----------------------|
| **1(主)** | 连续录像入队 `stream_router.c` 约 632 行 | 关键帧录 `sbuf/slen`(复用 Live 已有的 `par[]`+`tmp` 拼接结果)而非裸 `data`。继续丢独立 `is_param` NAL(已折进 IDR)。因每个 GOP 头都带参数集、worker 在 IDR 处切段 → **每个段首都自带 SPS/PPS**。 | `has_param` 相机不建 `tmp`,`sbuf==data`,录的字节与现状**完全一致**。 |
| **1(主)** | 事件片段入队 约 646 行 | 同上,改用 `sbuf/slen`。 | 同上。 |
| **1b** | 预录环 `stream_pre_push` 约 650 行 | 关键帧存拼好参数集的 AU(`sbuf/slen`),保证事件片段段首也带头。 | 同上,内嵌型无变化。 |
| **2(次)** | Live 起播门控 约 615 行 push + `stream_live_drain` | 把 push 的"可起播"标志从 `nc.is_key` 改为 `have_params`(需把 `have_params` 提到函数作用域)。`par_len==0` 且当前 IDR 无内嵌参数集时**保持 WAIT_IDR**,不喂垃圾、不刷屏,等拼得出头再起。 | 内嵌/已缓存参数集的相机第一帧即可起,行为不变。SYNCED 后照常连喂(此时 VPU 已有活动 SPS)。 |

实现要点:

- `have_params = nc.is_key && (nc.has_param || tmp != NULL)` 需从内层块(约 590 行)**提到函数作用域**,
  供录像/预录/Live 共用;`is_param` 分支不进 live/record(已有 `!nc.is_param` 守卫)。
- `sbuf/tmp` 在 `stream_route_video` 末尾 `free(tmp)`;record/pre_push 均**同步拷贝**入队,`free(tmp)` 前
  数据已落队,无 use-after-free。
- 段独立可解:worker 在 IDR 处 `rsdk_rec_rotate`;因每个 GOP 头 IDR 都带参数集,每段段首自然带头。

## 5. fix 3(SDP 参数集补种)— 技术可做,是否做待定

- 面向"参数集只在 SDP `sprop-parameter-sets`、从不带内发"的相机。
- 拉流库已确认为**仓库内 `SDK/OnvifClientLibrary`(带完整源码)**,facade 为 `nop::NopRtspClient`
  (`nop_rtsp.h`/`nop_rtsp.cpp`)。公有 API 仅 `open` / `setVideoCb` / `setAudioCb` / `play` /
  `stop` / `sendBackchannel` / `videoCodec` / 传输超时设置 —— **未暴露** SDP 参数集。
- 但 `sprop-parameter-sets` **在库源码里已被解析**(`rtsp/rtsp_rcua.cpp`、`media/media_util.cpp`),
  只是没经 facade 透出。故 fix 3 **可做**:给 facade 加一个取 sprop 的 glue 方法,连上后把 SPS/PPS
  seed 进 `par[]`(仅当带内 `par` 为空时用)。
- 代价:需**改这份 vendored 库**(加 facade 方法)。是否动它是设计取舍(架构约定倾向不改 vendor 源、
  只加薄 glue)。
- 实务上多数分离型相机会把 sprop 作为首批带内 NAL 注入,fix 1/1b/2 的带内缓存已覆盖大多数场景;
  fix 3 仅为"纯 SDP、从不带内发"的极少数相机兜底。

## 7. 验证计划

- 本机 Windows host **无法交叉编译**(aarch64 + hdal 依赖链)→ 上板 / 联调环境跑 `-fsyntax-only` 或整包编译。
- 功能验证:用**分离型参数集**故障相机,分别验:
  - 预览:切到该通道应正常出图,串口不再刷 `scan first header error`。
  - 录像回放:新录段回放正常(段首 IDR 带 SPS/PPS)。
  - 正常(内嵌型)相机:录像字节、预览行为与改前一致(回归)。
