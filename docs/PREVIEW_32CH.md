# 32 路子码流分屏实时预览 —— 实现方案与容量

> SoC：Novatek **NA51090 / NT98633**（VPU 硬解 + VPE 缩放 + VideoOut 4K 上屏）。
> 关键结论先讲：**录像不解码、预览才解码**；32 路子码流分屏是**子码流(≈640×360)**并解，
> 主码流只在单画面/放大时用；H.264 与 H.265 **都支持**。

---

## 1. 主/子码流分辨率

| 码流 | 典型分辨率 | 用途 | NVR 侧处理 |
|---|---|---|---|
| **主码流 main (`video`)** | 1920×1080(2MP)，部分机型 2560×1440(4MP) | 单画面 / 4 分屏 / 放大 / 全屏 / 回放 | 硬解（`mhal_vdec` 上限当前 1920×1088，4MP 需上调 `MHAL_DEC_MAX_W/H`）|
| **子码流 sub (`subVideo`)** | **640×360（360p）** 或 D1(704×480/720×576) | 6/9/12/16/**32** 多分屏预览 | 硬解，窗口小、像素率低 |

> 来源：NOP `getLiveCapabilities` 返回 `streamType:["audioAndVideo","audioAndSubVideo","video","subVideo"]`
> —— 每路相机同时提供主码流与子码流两路 RTSP。分屏预览一律取 **subVideo**。

**码流选择规则**（`app/preview` 编排，`nvr_stream_switch_stream`）：
- 多分屏（≥6 窗）→ 全部 **子码流**
- 单画面 / 全屏 / 数字放大 → 该窗切 **主码流**

## 2. 同时能解多少（并发容量）

解码不是按"路数"限，而是按 **总像素吞吐 (Mpix/s)** 限。**硬件权威值取自 NT98633/NA51090 数据手册**
（H.264/H.265 Decoder Feature）：

```
纯解码性能  = 1920×1080 @ 360fps  ≡  3840×2160 @ 90fps  ≈ 746 Mpix/s（总预算）
单实例最大帧 : 分辨率 up to 8192×8192；H.265 Main@L5.1 high tier / H.264 High@L5.2
自带 1/2、1/3、1/4 缩小帧输出（解码同时出缩略，正好喂分屏）
```

### 32 分屏最高支持多少（按 **20fps**）
每窗预算 = 746 Mpix/s ÷ (32 窗 × 20fps) ≈ **1.17 Mpix/帧/窗** → 折 16:9 约 **1440×810**。

| 32 分屏方案(每窗) | 32 路合计@20fps | 占预算 | 结论 |
|---|---|---|---|
| **640×360（子码流，与 4K 6×6 格物理尺寸匹配）** | ≈ 147 Mpix/s | **20%** | ✅ 富余，甚至可拉到 40~50fps |
| 960×540 (qHD) | ≈ 332 Mpix/s | 44% | ✅ 可行 |
| **1280×720 (720p) ← 32 分屏预算上限** | ≈ 590 Mpix/s | 79% | ✅ 上限（再高即超预算）|
| 1920×1080 | ≈ 1180 Mpix/s | 158% | ❌ 超预算，32 路 1080p 做不到 |

→ **32 分屏@20fps 最高每格 720p**（590 Mpix/s）；但 4K 屏 6×6 每格物理只有 640×360，
上到 720p 无意义，**实际用 640×360 子码流即可，且余量很大**。

### 单宫格最大解多少（主码流，按 **20fps**）
单画面只有 1 路，受**单实例最大帧**限，几乎不受总预算限：
- 单路 4K **3840×2160@20fps ≈ 166 Mpix/s**（仅占 22% 预算；HW 单实例本就能 4K@90）→ ✅ 轻松
- 解码器分辨率上限 **8192×8192**，主码流到 8MP/4K 都能单宫格全解。
- **答：单宫格最大可解 3840×2160(4K/8MP)@20fps**（余量充足）。

**结论**：
- 32 分屏 640×360 子码流@20fps → 只吃 20% 预算，**轻松实时**；理论上限每格 720p@20。
- 单宫格主码流 → 可解到 **4K(3840×2160)@20fps**（HW 单实例能 4K@90，20fps 毫无压力）。
- 硬件实例上限 `HD_VIDEODEC_MAX_IN = 64`，不是瓶颈；瓶颈是 746 Mpix/s 吞吐 + DDR 带宽。
- ⚠️ `mhal_vdec` 当前把每实例 max_mem 定在 1920×1088——**单宫格 4K 需把该实例的 max_dim 上调到 3840×2160**
  （按打开的窗动态给 max_mem，预览子码流实例仍留小，避免 32 个都占 4K 内存）。真机实测 DDR 池上限。

## 3. 实现要点：取流/录像 与 预览解码 解耦

这是 32 路能跑起来的核心——**编码帧旁路直写录像，免解码**；只有**可见窗口**才解码。

```
                每路相机(RTSP 主+子)
                        │
        ┌───────────────┼────────────────┐
        ▼(编码帧,免解码)                  ▼(仅可见窗)
   ┌─────────┐                      ┌──────────────┐
   │ 录像旁路 │ rsdk_rec_write_frame  │ mhal_vdec 硬解 │→ VPE 缩放 →┐
   │ 32 路并写│ (Annex-B 直落盘)      │ (≤当前分屏窗数) │           ▼
   └─────────┘                      └──────────────┘      VideoOut 拼接(4K)
```

1. **32 路全部取流 + 录像**：`nvr_channel` 每路拉 RTSP → `rsdk_rec_write_frame` 直写（编码帧，**不解码**），只受盘写带宽限。
2. **仅可见窗解码**：`nvr_preview` 按当前布局（1/4/6/9/12/16/32）为**在屏窗口**分配 `mhal_vdec` 解码器 + VideoOut 窗口。
3. **离屏通道跳过解码**：`vout_win = -1` → 帧路径不调 `mhal_vdec_send`（`nvr_channel` 头注释已声明此语义），**零解码开销**。
4. **翻页 / 改布局**：动态开/关解码器并重绑窗口；离屏窗口的解码器释放，像素预算回收。
5. **32 分屏布局**：4K(3840×2160) 上 6×6 网格，每格 ≈ 640×360，正好吃子码流原分辨率，无需放大。

## 4. H.265 / H.264 支持

**两者都支持**，硬解自动按码流类型选择：

- `mhal_vdec.h`：`typedef enum { MHAL_CODEC_H264, MHAL_CODEC_H265 } mhal_codec_t;`
- `mhal_vdec.c`：`d->codec = (codec==MHAL_CODEC_H265) ? HD_CODEC_TYPE_H265 : HD_CODEC_TYPE_H264;`
- 每路解码器按该通道实际码流(SPS/VPS)配置；主/子码流可各自不同 codec。
- 录像旁路对 H.264/H.265 都是 Annex-B 直落盘（`pteeeld` 帧头 + PES），与解码无关。

实测 DDR 内存池与 4K 拼接屏最大窗数，确定 32 分屏子码流帧率上限（15 或 25）。

## 6. 动态分配 + 预算准入（已实现）

不再用固定 1920×1088，而是**按每路实际分辨率动态分配 + 吞吐预算准入**：

- **预算记账** `platform/media_hal/mhal_budget.{h,c}`（纯 C，已主机单测 `test_mhal_budget`）：
  总预算默认 **746 Mpix/s**（数据手册 1920×1080×360，可 `mhal_budget_set_total` 按真机覆盖）；
  每路开销 = `w×h×fps`。
- **动态 max_mem** `mhal_vdec.c`：`cfg_dec_path` 用该路实际 `w/h/fps` 分配（单宫格 4K 分 4K，
  子码流分 640×360，16 对齐），不再一刀切；单实例帧尺寸上限 **8192×8192**。
- **准入 + 拒绝最新一路**：`mhal_vdec_open(chn,codec,w,h,fps,win,&d)` 先 `mhal_budget_try_reserve`：
  - 放得下 → 占用预算、正常开解码；
  - **放不下 → 返回 `MHAL_VDEC_EBUDGET`，不开这一路解码器**（就是最新添加/最新上线的那一路）。
- **在错误处上报**：`mhal_vdec_open` 与 `stream_router_open` 在**失败点**各打一条 `NVR_LOGE`
  （“chn N 超出解码能力(预算超限) → 该路仅录像不预览”）；并置 `stream_chan.decode_denied=1`，
  经 `nvr_stream_decode_denied(mgr,chn)` 供 UI/NOP 查询提示（**录像不受影响，只是不出预览**）。
- 关闭解码器 `mhal_vdec_close` 归还预算，翻页/切布局时预算自动回收。

> 分辨率来源：`nvr_stream_chan_cfg_t.enc_w/enc_h/fps`（应由 ONVIF `GetVideoEncoderConfiguration` 回填）；
> 未填时按码流类型估算（主码流 1080p / 子码流 640×360 / 20fps）。真值回填后预算更准。

单测实证（`test_mhal_budget`）：32×子码流 640×360@20 = 147 Mpix/s(20%) 全放行；
1080p@20 逐路加到**第 18 路满、第 19 路被拒**；单宫格 4K@20 = 166 Mpix/s 放行。
