一、先分清"liveView 延迟 1 分钟"是哪条链路
代码里有两条完全不同的 live 通路,根因不一样:

通路	代码	有无背压/丢帧
本地 HDMI 上屏	puller → LiveQueue(cap 8 / 500ms 丢旧)→ VDEC → VOUT	✅ 有界(≤500ms)
远程手机 App(TUTK/P2P)	puller → nvr_rtsp_live_feed() → 阻塞 send()	❌ 无队列、无丢帧、阻塞发送
分支是 tutkagent、近期在做 App/TUTK,1 分钟延迟基本可锁定在远程 App 通路。因为本地通路的 LiveQueue 明确把延迟压在 500ms(丢旧帧),不可能自己涨到 1 分钟——除非是相机侧 SDK 内部缓冲。

二、LiveView 延迟 —— 差异
🔴 差异 1(最可能的元凶):远程 App live 无队列 / 阻塞发送
nvr_rtsp_live.c:1132 nvr_rtsp_live_feed 在 puller 线程里(被 stream_router.c:538 同步调用)直接:


send_annexb() → sess_send() → send_all() → 阻塞 send()   (nvr_rtsp_live.c:148)
没有每会话发送队列,不丢帧,send() 一直阻塞到全部字节写进 socket。
P2P 隧道带宽有限。当相机码率 > 隧道带宽,内核发送缓冲越积越多,App 收到的永远是越来越旧的帧 → 延迟无上限累积,几十秒到 1 分钟正是这么来的。
行业做法:每会话一个小的发送环形队列;队列积压超阈值就丢到最近一个 IDR(丢一整段 GOP 追最新);send() 用非阻塞 + 超时,发不动就丢而不是堵。本地的 LiveQueue 已经是这个思路,但远程通路完全没抄过来。
附带伤害:阻塞发送卡在 puller 线程 → 拉不动相机下一帧 → 相机侧 TCP 积压 → 恢复时突发 → 触发 RTP gap → 录像也跟着打 gap 标记。一条 App 连接能把该通道的录像拖断。
🔴 差异 2(本地 HDMI):送解码器时间戳单位错误
mhal_vdec.c:262


item.user_bs.timestamp = (UINT64)ts * 1000;   /* 90kHz→us 的换算按需精化 */
ts 是相机透传的 RTP 90kHz 时间戳,却当成 ms 再 ×1000 当 µs。30fps 时每帧 RTP +3000 → ×1000 = 每帧 300 万"µs"≈3 秒。若 VOUT 按此时间戳排程显示,帧被排到很远的未来,延迟会快速累积。行业做法:统一 Time Mapper,RTP ts 正确换算到显示时钟,或首帧对齐后用相对递增。

🟠 差异 3:相机侧 SDK jitter buffer 深度未知/未设界
stream_puller.cpp:22 nop::rtspLibInit(256) —— 256 缓冲池,RTP/TCP 强制交错。真正的抖动缓冲/重组在闭源 NopRtspClient(NT12-SDK,不在仓库内)。行业做法:jitter buffer 深度可配且以 ms 为界(如 200ms);本地已有 config/streaming.json 的 jitter_ms:200 但这个键根本没被读(死配置)。

三、录像"断" —— 差异
🔴 差异 4:单一 record worker 线程 + 满即丢帧
全系统只有一个 worker 线程写所有 64 条队列(stream_record_worker.c:218),每轮每路预算 512KB,空闲 50ms。
RecordQueue 满(96)时 stream_hub.c:151 直接返回 -1、帧被 free 丢掉——头文件写的"不丢帧、调用方须先 drain",但 puller 侧根本不 drain(drain 在 worker 线程),所以背压退化成丢帧 → 录像 gap。
行业做法:requirement 文档(rtsp优化.md)自己都写了——每块物理盘 1~2 个 worker,固定映射(worker_id = stream_id % N),写盘与回收分线程。当前是"64 队列 → 1 线程",磁盘一抖全线积压。
🔴 差异 5:覆盖回收全索引扫描,内联在写路径
rsdk_rec.c:51-54 覆盖模式每开新段(chunk 翻转)就调 rsdk_index_invalidate_chunk,而它(rsdk_index.c:85)线性扫描整个盘的索引(O(chunk×slots),8TB/8MB ≈ 数百万次 64B pread),同步跑在唯一的 record 线程上。盘一旦写满进入循环覆盖,每次翻段都是一次巨型停顿 → 队列填满 → 丢帧 → 周期性录像断。这是磁盘满之后最典型的断因。行业做法:空闲位图/空闲链 O(1) 回收 + 独立后台回收线程,绝不在写路径做全表扫描。

🟠 差异 6:分片只按 chunk 写满,无按时间切片、新段不 IDR 对齐
rsdk_rec.c:128 只有"帧放不下当前 chunk → 闭段开新段",没有按时间(如 60s)切片,而且新段从下一帧起写,可能是 P 帧 → 回放走到段边界会花屏/找不到参考帧,表现为"断一下"。Recorder 状态机只有 WAIT_IDR/RECORDING,缺 requirement 建议的 ROTATE_PENDING(到点后等下一个 IDR 再切新段)。行业做法:定时切片 + 每段从 IDR 开始。

🟠 差异 7:录像时间戳用写盘时刻,不是采集时刻
stream_record_worker.c:117-118 f.wall_time = time(NULL) —— worker 若滞后几秒,录进去的时间就偏了 → 回放时间轴错位、日历/进度条看着"跳/断"。行业做法:Time Mapper,帧头带采集时刻 wallclock,而不是写盘时 time()。

🟠 差异 8:TCP 下 RTP seq 缺口启发式易误报
stream_router.c:420 max_pkts = len/700+3 判定 seq 跳变 → disc_mark → worker 打 gap 标记。TCP(已强制)本不该丢包,大帧/合法分片可能把它误判成缺口 → 盘没问题也在录像里打"断"标记。requirement rtsp架构.md 也指出 TCP 下 seq 不再代表丢包,应只做参考而非核心连续性判据。

🟡 差异 9:无 O_DIRECT,仅段界 fsync
裸盘 pwrite 走页缓存,只在段开/段闭 fsync(rsdk_rawdev.c)。断电会丢当前 chunk(8–32MB)内已收未刷的帧。行业做法:周期性 fsync 或 O_DIRECT + 环形直写。

四、单 HDD / 多 HDD —— 差异
现状(其实做得接近行业 JBOD NVR):

rsdk_group_t = 多盘组,每段按负载均衡选盘(rsdk_balance.c:121,score=带宽+填充+压力,带通道亲和);单盘=退化的 n=1 组。
存储层有扫描/识别/格式化/组装/热插拔/缺盘降级/SMART 轮询(components/storage/)。缺盘继续录、故障盘 balance 跳过。
vs 行业的差异:

维度	当前	行业中高端 NVR
冗余	❌ 纯 JBOD,单盘坏=该盘录像全丢	RAID1/5/10 可选
回收调度	每盘各自、内联写路径、全索引扫描	全局后台回收,O(1) 空闲管理
单盘覆盖回收	更痛:整盘一个索引,扫描更大	分区/分桶索引
盘故障切换	软亲和,故障后新段换盘	同左(基本对齐)
坏块容忍	✅ 有(标坏 chunk 换盘续写)	对齐
多盘的功能面基本够用;痛点是回收/索引的可扩展性(差异 5),盘越大越明显,单盘满盘循环时最容易触发录像断。
