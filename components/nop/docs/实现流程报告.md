## 1. 目标与范围

依据 `NOP_SDK_架构设计_v3`（三平面、内置 TUTK）与 `NOP_SDK_NOP协议实现计划`
（里程碑 N0–N4），新建一个**自包含、跨工具链**（与 TUTK SDK 一样可按不同编译链
独立编译）的 C SDK，所有内容收敛在 `nop_sdk/` 一个文件夹下。

本轮交付里程碑 **N0**：协议核心可在纯 x86 上用 mock + ctest 全量跑通，作为后续
所有 handler 与 TUTK/ONVIF 接入的地基。**不碰**网络/TLS/真机硬件——这些经
`nop_transport_if` 与 `hal_registry` 注入，零返工。

## 2. 实现顺序（严格自底向上，每步可独立编译 + ctest 守门）

与实现计划的 S1–S8 对齐，实际落地顺序：

1. **目录脚手架 + 构建系统**：按 v3 布局建树；顶层 CMake（静态+动态 `nopcore`）、
   三份交叉编译 toolchain 文件、`build.sh`/`build.bat`。
2. **第三方隔离**：vendored cJSON 进 `third_party/cJSON/`，仅由 `base/nop_json`
   引用。
3. **公共 ABI 头**：`include/nop_sdk/` 唯一对外头集合（稳定 C ABI）。
4. **base/ 公共原语**：`nop_err`（状态码+映射）、`nop_log`（分级+sink）、
   `nop_mem`（分配封装）、`nop_json`（cJSON 薄门面）、`nop_map`（djb2 哈希表，
   取代 leo 的长 strcmp 链）。
5. **osal/ 移植契约 + 实现**：`osal.h`（递归互斥 + 单调时钟）；posix 与 windows
   两份 port，`linux_uclibc` 复用 posix。
6. **nop/ 协议核心**：`nop_envelope`（信封编解码）、`nop_router`（注册/分发 +
   batchCmd 递归 + 501 兜底）、`nop_longpoll`（事件位图）。
7. **capability/ 单一事实来源**：`cap_registry`（能力点亮位掩码 + 门控判定 +
   getDeviceCapabilities 自动汇总）。
8. **transport/ 注入点**：`nop_transport_if` 契约 + `transport_mock` 内存回环
   后端。
9. **hal/ 硬件抽象**：`hal_registry`（按 id 注册 vtable）+ `ports/stub` 全能力
   打印桩（开箱即跑）。
10. **business/caps handler + app 门面**：批 1（device/auth/system，纯协议）+
    批 2（stream/ptz/light，经 HAL 门控）；`nop_app` 一键门面装配全栈。
11. **tests + example**：5 个 ctest（map/envelope/router/transport/dispatch）+
    `ipc_demo`。
12. **文档与报告**：README、移植指南、命令矩阵、三份报告。

## 3. 关键设计落地

- **传输彻底注入化**：`nop/` 只做「JSON bytes 进 → JSON bytes 出」，不 link
  socket/TLS。三类来源（P2P/Socket/LVGL）将来共用同一 `nop_router`，TUTK 只是
  又一个 `nop_transport_if` 后端。
- **单一事实来源**：一份能力集同时驱动①命令路由门控 ②getDeviceCapabilities
  汇总（同源，不手写能力清单）。
- **未注册即 501**：命令未注册、能力未点亮、或对应 HAL 未注册，统一稳定回 501，
  不崩。
- **handler 边界纪律**：handler 只做「校验 args → 调 HAL/编排 → 填 content」，
  硬件一律经 `hal_registry`，绝不直连芯片 API。
- **强分层单向依赖**：`app → business → {nop,capability} → transport →
  {osal}`，所有层 → `base`；第三方（cJSON）封在 `base/nop_json` 内。

## 模块记录 · ONVIF 客户端抽取（2026-06-27）

> 约定：每完成一个大模块在此追加一条记录。本条为「ONVIF 客户端」。

**目标**：把现有 Happytimesoft ONVIF 客户端库（`onvif_sdk/OnvifClientLibrary`）抽取
进 SDK，**原文件一字不改**——只做「复制 vendored + 一层调用适配」。

**可行性结论**：可行且干净。该库本身是自包含、无 UI 的纯协议库（Makefile 仅编
`bm/`+`http/`+`onvif/`、只链 openssl；FFmpeg/SDL/Qt 都在桌面工程里，不在库内），
公共 API `onvif_api.h` 以 `extern "C"` 暴露，可直接 C 调用。

**落地内容**：
1. **vendored（零修改）**：`onvif_sdk/OnvifClientLibrary/{onvif,bm,http,openssl}` +
   `stdafx.h` 原样复制到 `third_party/onvif/`，加 `libssl/libcrypto.so` 软链接。
2. **适配层（唯一接触面）**：`src/onvif/onvif_adapter.cpp`（C++ 编译、导出 C ABI），
   对内提供 `nop_sdk/nop_onvif.h`：`nop_onvif_global_init / discover /
   get_stream_uri`。调用序列对齐库自带 OnvifTest 示例（network_init + 缓冲区 + 日志
   → set_probe_cb + start_probe → 每设备 GetProfiles + GetStreamUris）。
3. **构建裁剪**：新增 `NOP_WITH_ONVIF`（默认 OFF）。开启时单独建 `nopcore_onvif_obj`
   对象库（CXX，独立 include/defines，`-w` 静默第三方），其目标对象并入静态/动态
   `nopcore`，链 vendored openssl 1.1 + pthread；关闭时核心仍是纯 C、零 ONVIF 依赖。
4. **示例**：`examples/onvif_client_demo.c`（纯 C，仅用 `nop_onvif.h`）——LAN 发现
   设备并取各设备 RTSP 流地址。

**依赖隔离铁律遵守**：ONVIF 头/库只进 `src/onvif/` 适配器与 `third_party/onvif/`，
`nop/`/`business/`/`base/` 一律不 include ONVIF；协议核心仍可在无 ONVIF 下纯 C 构建。

**验证状态（已编译运行通过，2026-06-27）**：
- 默认构建（ONVIF OFF）：5/5 ctest 全绿，未受影响。
- ONVIF 构建（ONVIF ON，g++ 13.3）：vendored 31 文件 + 适配器全部编过，静态/动态
  `nopcore` 与 `onvif_client_demo` 链接成功；5/5 ctest 仍全绿；`onvif_client_demo`
  实跑 WS-Discovery → 干净退出（本机网络无 ONVIF 设备，报 0 台，整条
  init→probe→shutdown 链路验证通过）。
- 链接细节经逐行核对并验证：HT_API 空宏、各工具头自带 `extern "C"`、`stdafx.h`
  仅 Windows 分支；字段名 `binfo.XAddr`/`profiles->stream_uri`/
  `TransportProtocol_RTSP`/`AuthMethod_UsernameToken` 均正确。
- **bring-up 期间发现并修复 1 处集成问题**（非改动 vendored 文件）：vendored
  `log_init(NULL)` 会 `strncpy(NULL)` 崩溃；因其日志写入对 `fp==NULL` 有保护、
  会安全空转，故适配器**改为不调用 log_init**（保持安静、不写日志文件），而非传
  文件名。
- 运行依赖：vendored openssl 1.1（host/linux）；demo 已设 BUILD_RPATH，免
  `LD_LIBRARY_PATH` 直接运行。

## 模块记录 · ONVIF 客户端「完整能力集」（2026-06-27）

> 在前一条「ONVIF 客户端抽取」（发现 + 取流）基础上，补齐 **支持 ONVIF Client 的
> 全部代码内容**。原 onvif 文件仍**零改动**，全部新增能力都在适配层 + 公共头。

**新增/扩展接口**（`include/nop_sdk/nop_onvif.h`，共 **42 个 `nop_onvif_*` C API**，
已在 `libnopcore.so` 验证导出齐全）：
- **运行时**：global_init / global_cleanup
- **发现**：discover（一次性 probe）+ monitor_start/stop（持续 Hello/Bye）
- **设备句柄**：device_create / set_auth / set_timeout / destroy / last_error
  （不透明句柄 `nop_onvif_device_t`，内部封装 `ONVIF_DEVICE`）
- **设备服务 tds**：get_device_information / get_capabilities / get_services /
  get_system_datetime / set_system_datetime_now / reboot / factory_reset
- **媒体 trt**：get_profiles / get_profile / get_stream_uri / get_snapshot_uri /
  get_snapshot(+free_buffer) / get_video_source_count
- **PTZ**：get_node_count / continuous_move / stop / relative_move /
  absolute_move / goto_home / goto_preset / set_preset / remove_preset /
  get_presets
- **成像 img**：get_imaging_settings / set_imaging_settings（亮度/对比度/饱和度/
  锐度，带有效位）
- **事件 tev**：events_create_pullpoint / events_pull / events_unsubscribe（拉点订阅）
- **固件/系统**：firmware_upgrade / system_backup / system_restore

**实现策略**：能用 vendored 高层 `onvif_api.h`（直接操作 `ONVIF_DEVICE` 并把结果
存进结构体）的就用高层（设备信息/时间/profiles/快照/事件/固件等）；高层没有的
控制类（PTZ 连续/相对/绝对移动、停止、预置位、Home、成像 set、快照 URI、reboot、
工厂复位）用 `onvif_cln.h` 的 `onvif_ptz_*/onvif_img_*/onvif_trt_*/onvif_tds_*`
低层接口，按已核对的 REQ/RES 结构填参。响应里自带分配的链表（PTZ 预置位、事件
通知）用库自带 `onvif_free_PTZPresets / onvif_free_NotificationMessages` 释放。

**验证（g++ 13.3）**：适配层（31 vendored + adapter）**一次编过**（结构体字段/签名
全部一次命中）；`libnopcore.{a,so}` 链接成功，`nm -D` 确认 42 个 `nop_onvif_*`
导出齐全；5/5 ctest 仍全绿；扩展后的 `onvif_client_demo` 实跑：发现 → 建句柄 →
查设备信息/时间/profiles/流地址/快照URI/PTZ 节点数 → 干净退出（本机无 ONVIF 设备，
0 台，链路完整）。
