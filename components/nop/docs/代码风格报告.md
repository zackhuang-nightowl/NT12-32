# NOP SDK 代码风格报告

> 语言标准：C11（无异常、无 RTTI）｜ 编译：`-Wall -Wextra` 零警告
> 核心原则：**每个命名都能完整看出它代表的内容**。

## 1. 命名规范（最高优先级）

要求：标识符的名字必须自解释，读名即知其义，禁止含糊缩写。

| 类别 | 规则 | 示例 |
|---|---|---|
| 公共函数 | `nop_<模块>_<动作>()` | `nop_app_dispatch` `nop_router_register` `cap_registry_is_enabled` |
| 公共类型 | `nop_<名词>_t` / 模块前缀 | `nop_app_t` `nop_status_t` `cap_registry_t` `hal_system_if` |
| 宏 / 枚举 | `NOP_*` / `CAP_*` / `HAL_*` 全大写 | `NOP_OK` `CAP_STREAM` `HAL_VIDEO` |
| 内部静态函数 | 动词短语，handler 统一 `handle_<命令>` | `handle_get_device_info` `dispatch_one` `auto_light_capabilities` |
| 结构体字段 | 完整单词 | `capability_registry` `routes_by_func` `write_cursor` `pending_bits` |
| 局部变量 | 完整单词，体现领域含义 | `device_info` `channel_count` `capability_index` `direction_name` |

**反面教材 → 已修正**：`biz`→`business`、`capreg`→`capability_registry`、
`h_xxx`→`handle_xxx`、`di`→`device_info`、`rt`→`route`、`lp`→`longpoll`、
`mx`→`mutex`、`vid/sys/lt`→`video/system/light`、`djb2`→`hash_djb2`。

唯一例外：纯循环计数器在含义明确处可用 `i`/`n`——但凡承载领域含义一律用全名
（如用 `channel_index` 而非 `i` 来遍历通道）。

## 2. 文件组织

- **公共/私有分离**：对外稳定 ABI 全在 `include/nop_sdk/`；`src/` 全私有实现，
  内部头与 `.c` 同目录。
- **一个能力集一个文件**：`src/business/caps/cap_<group>.c`，文件名即其职责。
- **自注册**：每个 handler 文件导出 `cap_<group>_register(router)`，新增命令
  零侵入协议核心。
- 每个文件顶部 `@file`/`@brief` 注释说明职责与边界。

## 3. C ABI 与接口约定

- **不透明句柄**：对外只暴露 `typedef struct nop_app nop_app_t;` + 函数；内部
  结构体定义不出头文件。
- **配置即结构体**：init 走 `const nop_xxx_config_t*`，预留 `reserved[]` 字段向
  后兼容；调用方零初始化即可。
- **vtable + opaque ctx**：HAL/transport 是函数指针表 + 不透明 `ctx`（Beningo
  HAL 模式 / AWS coreMQTT transport 模式）。
- **统一返回码**：内部一律 `nop_status_t`；仅在 `nop/` 边界映射为协议 statusCode
  （200/400/501）。

## 4. 内存与所有权

- 分配统一经 `base/nop_mem`（`nop_malloc/calloc/realloc/free/strdup`），便于将来
  换静态/池后端；嵌入式热路径不动态分配。
- **所有权显式标注**：注释写明谁拥有、谁释放。例：`nop_envelope_build()`
  **消费** `response->content`；`nop_request_t.args` 为**借用不拥有**。
- 失败必返错误码，绝不崩；所有指针入口做 NULL 防护，`osal_mutex_*` NULL 安全。

## 5. 错误处理

- 分发器对任何输入都产出**合法响应信封**：坏 JSON→400、未知/未点亮→501、
  handler 返回非 OK→按映射置码并丢弃半成品 content。
- 业务错误走 `content.error`，**不设全局错误码**（对齐 NOP 规范）。

## 6. 并发与可移植

- `router` / `cap_registry` / `longpoll` 的共享状态加 `osal_mutex`（命令线程与
  事件线程并发）。
- 协议/业务层**只调 osal，不直接调系统 API**，保证 arm-uClibc / x86 / windows
  三跑同一份源码。

## 7. 第三方隔离

- cJSON 仅由 `base/nop_json` 引用；其余代码一律 `#include "base/nop_json.h"`，
  不直接 include 第三方头——将来替换 JSON 库只动一处。
- **vendored 第三方（cJSON / ONVIF 客户端库 / 将来 TUTK）原样收录、零修改**，
  因此**不受本文命名规范约束**；它们各自的命名风格保持原样，便于后续整包升级。
  我方代码只通过一层适配器接触它们：`base/nop_json`(cJSON)、
  `src/onvif/onvif_adapter.cpp`(ONVIF) ——**适配器本身严格遵守本文全部规范**
  （如 `nop_onvif_get_stream_uri`、`probe_trampoline`、`copy_scopes`、
  `device`/`result` 等全词命名）。
- 适配器对外只暴露纯 C ABI（`nop_sdk/nop_onvif.h`），即使内部是 C++ 实现，
  其余 C 代码与构建对第三方语言无感知。

## 8. 排版细节

- 4 空格缩进，无 Tab；左大括号函数体另起一行、控制流同行（K&R 变体）。
- 指针 `*` 贴变量名；`(void)param;` 显式标注未用参数。
- 公共 API 带 Doxygen 注释（`@brief`/`@param`/`@return`）。
